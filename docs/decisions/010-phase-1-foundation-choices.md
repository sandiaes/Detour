## Context

Phase 1 (project scaffolding) asked for a monorepo, a mobile shell, a FastAPI service with
anonymous installations, empty `geo` and `app` schemas, a generated API client, CI, an Android
build, and Render and Supabase deployment configuration. ADR 001 asked for exact versions to be
recorded in this phase. Some requests pulled in different directions, and a few choices had to be
made that no earlier document covers.

## Decisions

### 1. Layout and tooling

- One repository: `apps/mobile` and `packages/shared` are **npm workspaces** (root
  `package-lock.json`); `services/api` is a separate Python project installed with pip. Expo's
  Metro and `expo prebuild` handle the workspace layout; this was checked with a full Metro bundle
  and an Android prebuild.
- Python: ruff (lint and format), mypy strict, pytest. JavaScript: prettier, eslint
  (`eslint-config-expo`), tsc, jest (`jest-expo`, React Native Testing Library).
- The contract is `packages/shared/openapi.json`, exported by
  `services/api/scripts/export_openapi.py`. Types are generated by `openapi-typescript`; the typed
  client is `openapi-fetch`. CI fails on drift in either direction.

### 3. Anonymous installation tokens are stateless

Registration returns `dt1.<installation id>.<HMAC-SHA256 signature>` keyed with
`DETOUR_TOKEN_SECRET`. The token check verifies the signature and needs no database.

Why: the brief asks for the `geo` and `app` schemas to be **empty**, while `data-model.md` puts a
`token_hash` in `app.installation`. A table would contradict the first; a signed token satisfies
both and makes registration and the check work even when the database is paused (Supabase Free).

Consequences: tokens cannot be revoked individually; changing the secret invalidates every
installation, and the app then registers again by itself; installations have no server-side record
until Phase 4 adds `app.installation` (id, created and last-seen times, home currency) when trips
first need a foreign key. Tokens issued now stay valid then, because they carry the id.
`data-model.md` is amended accordingly. Registration is unauthenticated and unbounded, which is
acceptable while it writes nothing; add rate limiting in Phase 9 if the service is shared.

### 4. The Android build is a release-variant APK, not an `expo-dev-client` build

The brief says "development builds"; ADR 008's addendum (spike S1) replaced them with release
variants that have the JavaScript bundled in, because a development build needs a development
server on a computer and the owner has none. The Phase 1 workflow follows the ADR, so the phone
can call the deployed backend with nothing else running. The native code, and the rule against
Expo Go and hand-edited native projects, are unchanged. The APK is still signed with the public
React Native debug key; the project's own keystore (GitHub Actions secret, applied without
hand-editing the native project) is **not** done in Phase 1 and must precede any build that is
kept for real use.

### 5. Smaller choices

- **No navigation library.** Architecture 4.1 defers the choice to Phase 5 and an ADR. The shell
  uses a tab bar held in React state, with Create Trip and Itinerary opened from Trips.
- **Two health endpoints.** `GET /v1/health` is liveness and never touches the database (Render's
  health check uses it, so a paused database does not restart the service). `GET /v1/health/ready`
  checks the database and the two schemas and answers 503 otherwise.
- **Migrations run in `start.sh`**, because Render's free plan has no pre-deploy command. In
  Phase 1 a failed migration is logged as an error and the API still starts, so `/v1/health`
  stays reachable; revisit this once tables exist.
- **The first migration creates only the two schemas.** PostGIS is not enabled by a migration: on
  Supabase it is switched on in the dashboard (`extensions` schema), and its availability on the
  Free plan is unconfirmed. Phase 2 creates the extension where it first needs it. The Alembic
  version table lives in `public`, so `geo` and `app` stay empty.
- **Map style and credits come only from the backend.** `GET /v1/config` returns them; the app has
  no built-in fallback and shows an error with a retry instead. The attribution rule from spike S1
  (visible at start, collapses after 5 s or on a real user gesture, an "i" button restores it) is
  implemented in `AttributionBar` and tested.
- **Structured logging** writes JSON to stdout with redaction by key and by pattern (bearer
  tokens, URL credentials, Detour tokens). Request logs carry method, path, status and duration;
  never query strings, headers or bodies.
- **`httpx2` is not adopted.** Starlette's test client prints a deprecation notice recommending
  that package. It was not vetted, so the pinned `httpx` stays and that one warning is filtered in
  `pyproject.toml`.
- **A dependency policy check** (`tools/check_dependencies.py`) runs in CI and fails if a manifest
  or the npm lock file lists a known LLM or generative-AI library (CLAUDE.md constraint 1, KPI
  "Runtime LLM calls").

## Alternatives considered

| Alternative | Why not |
|---|---|
| `app.installation` table now, with a hashed token | Contradicts "empty schemas"; makes registration depend on a database that may be paused |
| `expo-dev-client` development build | Needs a development server (ADR 008 addendum) |
| React Navigation or Expo Router now | Choice belongs to Phase 5 (architecture 4.1) |
| pnpm or Yarn workspaces, or uv | No benefit that justified another tool for the owner to learn; npm and pip work on Render and in CI |
| Failing the start when migrations fail | Would also take `/v1/health` down, hiding the cause behind a Render restart loop |

## Consequences

- A reviewer can check the whole foundation from CI alone; nothing needs a local toolchain.
- Phase 4 owes `app.installation` and a decision on rate limiting; Phase 9 or earlier owes the
  signing key; Phase 5 owes the navigation ADR.
- Upgrades (Expo SDK, MapLibre, FastAPI) are planned tasks against this table.
- GitHub warns that `actions/checkout@v4` and `actions/setup-python@v5` run on a deprecated Node
  runtime; bump them in a planned maintenance change.
